# Working rules for this repository

These override default behavior. Follow them exactly.

1. **Ask before coding**: if anything is ambiguous or you have a design/scope question before
   writing code, use `AskUserQuestion` to ask first — don't guess, implement, and explain the
   guess afterward.

2. **Running tests/lint/commit/push**: don't run `pytest`, lint, `git commit`, or
   `git push` unless the user explicitly asks for it, or it's genuinely necessary to verify the
   specific change you just made (e.g. confirming a bug fix actually fixes the bug). Implementing
   or fixing code does not by itself imply "and then test/lint/commit/push it."
   - When a test run is genuinely necessary, scope it narrowly — the specific test file/module/
     package the change touches — never a full-suite run, unless the user explicitly asked for one.

3. **Investigation budget [IMPORTANT]**: if a task needs investigation (reading code, searching, tracing a
   bug), budget roughly 1,000 tokens of exploration for it. If you hit that limit and need more,
   stop and ask the user for permission before spending more.

4. **Claude session reference**: While creating commit and raising PR for GitHub, do not
   include Generated by Claude Code and Claude session references within the description.

5. **Commit Monitoring**: While raising commit, do not keep running the Claude, instead use monitoring to
   avoid spending tokens with a hook to identify when it is done and act on it.

6. **CHANGELOG.md entry style**: keep new `[Unreleased]` entries short — one or two lines,
   what changed from a reader's point of view, no file paths/function names/implementation
   rationale. That level of detail belongs in the commit message or PR description, not the
   changelog. This applies going forward only — don't rewrite past released versions' entries
   to match.

7. **README.md**: add/update the README.md from a user perspective rather than technical. For technical
   please create documents within docs/ folder.

## Python conventions

These apply on top of the rules above.

8. **Tooling**: use `uv`, never bare `pip` or `python -m venv`. Add dependencies with `uv add`
   (`uv add --dev` for dev tools) so `pyproject.toml` and `uv.lock` stay in sync; never edit
   `uv.lock` by hand. Run tools through `uv run`.

9. **Layout**: source lives in `src/<package>/`, tests in `tests/`. Keep the package typed
   (`py.typed`). The version lives only in `__version__` in the package `__init__.py`.

10. **Style**: Ruff handles lint and formatting (line length 100); mypy runs in strict mode, so add
    type hints to all new code. Target Python 3.11+ and don't use syntax or APIs newer than the
    oldest tested version without checking CI's matrix.

11. **Scoped checks**: when verification is genuinely needed (see rule 2), run only what the change
    touches, for example `uv run pytest tests/test_x.py`, `uv run ruff check <file>` or
    `uv run mypy <file>`. Coverage must stay at or above the minimum in `pyproject.toml`. Put slow or end-to-end tests in
    `tests/integration/`; they are excluded from the default run and only run with `-m integration`.

12. **Dependencies and releases**: keep runtime `dependencies` minimal. Don't change the version
    or publish; releases are cut by the maintainer through a GitHub release.
